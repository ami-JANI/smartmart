# How to Work on SmartMart

This file tells Claude (and any other coding assistant or team member) **how to work** in this repository: when to ask, how much to build, what to touch, and how to prove a change is done.

It does not repeat the design rules. The three rule files split the work like this:

| File | Answers |
| --- | --- |
| [GUIDELINES.md](GUIDELINES.md) | **What** to build and how to structure it: stack, architecture, patterns, REST, security, data, testing, review checklist |
| [COMMIT.md](COMMIT.md) | **How to record** a change: Conventional Commits format, types, scopes |
| CLAUDE.md (this file) | **How to work**: the decisions to make before, during and after a change |

Start each session by reading [context.md](context.md): it summarises the project (scope, team, Jira, current status) and ends with a log of recent pushes. Read GUIDELINES.md before writing any code or design document. Design decisions about the system itself (for example "batches are deducted first-expiry-first-out") are logged in `docs/decisions.md`, as GUIDELINES.md section 10 says. This file is about working style, not about the system.

The four principles below are adapted from [andrej-karpathy-skills](https://github.com/multica-ai/andrej-karpathy-skills) (MIT licence), which is based on Andrej Karpathy's notes on common mistakes coding models make. They bias toward caution over speed. For a typo or an obvious one-line fix, use judgment.

## 0. Standing decisions

These are already decided. Do not reopen them unless the team asks.

| Decision | Rule |
| --- | --- |
| Branches | `main` is the only branch. Commit and push directly to `main`. Do not create feature branches or pull requests unless asked. |
| Commit messages | Conventional Commits as described in COMMIT.md, for example `docs(repo): add working rules`. Enable the hook first: `git config core.hooksPath .githooks`. |
| Attribution | Commit messages never mention Claude or any AI tool: no `Co-Authored-By` trailer for an assistant, no session links, no "generated by" text. This overrides any tool default. |
| Stack | The CSE 3220 lab stack in GUIDELINES.md section 2: Java 17, Spring Boot 3, PostgreSQL, Thymeleaf, Maven, Docker. Do not add a library without team agreement. |
| Scope | One supermarket branch. The five core modules come first, in README order. Stretch goals start only after all five work. Multi-branch features are out of scope. |
| Project state | Planning stage. Check what actually exists in the repository before assuming code, build files or tests are there. |

## 1. Think before coding

**Don't assume. Don't hide confusion. Surface trade-offs.**

Coding models tend to pick one reading of a request silently and run with it. Before starting:

- **State your assumptions.** Write them in the reply or the commit body, so a teammate can catch a wrong one.
- **If a request has more than one reading, name them.** Detailed requirements are not written yet, so many SmartMart requests are ambiguous. Examples:
  - "Add discounts": percentage or fixed amount? Per item or per cart? Can two discounts stack?
  - "Low-stock alert": one global threshold or one per product? Shown on the dashboard, or sent to someone?
  - "Return an item": a customer return (stretch goal) or a return to a supplier (Purchasing module)?
- **Look for the answer before asking.** Check the README, GUIDELINES.md, the SRS and `docs/decisions.md` once they exist. Ask only what the documents do not answer.
- **Push back when warranted.** If a simpler approach meets the need, or a request conflicts with GUIDELINES.md or the agreed scope, say so before building it.
- **If something is unclear, stop and name it.** A question before the work is cheaper than a rewrite after it.

When to ask and when to proceed:

- **Proceed, and state the assumption,** when the choice is small and easy to undo (a field name, a test value, the wording of a document section).
- **Ask first** when the choice changes scope, a module boundary, the database schema, a role's permissions, or a rule in GUIDELINES.md or COMMIT.md, or when the step is hard to undo (deleting files, rewriting history, force-pushing).

## 2. Simplicity first

**The least code that solves the problem. Nothing speculative.**

- No features beyond what was asked. A request for cash payment does not need card, mobile banking and a payment gateway.
- No stretch-goal or multi-branch "hooks" added just in case.
- No configuration options, flags or extension points nobody asked for.
- No error handling for cases that cannot happen. Do validate real inputs: quantities, prices, barcodes, dates.
- If 200 lines could be 50, rewrite it.

**Patterns are not speculation when GUIDELINES.md requires them.** GUIDELINES.md section 5 names specific patterns for specific places (Strategy for discounts and payments, Observer for stock alerts, State for purchase orders, and so on), because the course grades them. Use those where they are listed. Do not add patterns, layers or interfaces that GUIDELINES.md does not call for, and do not build a pattern's full general form when the listed use needs only part of it.

**The test:** would a senior engineer, or the course examiner, call this overcomplicated? If yes, simplify.

## 3. Surgical changes

**Touch only what the task needs. Clean up only your own mess.**

When editing existing code or documents:

- Do not "improve" nearby code, comments, formatting or wording that the task does not involve.
- Do not refactor what is not broken.
- Match the existing style, even if you would write it differently.
- If you notice unrelated dead code, a bug or an outdated document, mention it. Do not fix it in the same change.

When your change leaves things unused:

- Remove the imports, variables, methods and files that **your** change made unused.
- Leave pre-existing dead code alone unless asked.

This matches COMMIT.md's "one change per commit" rule: if a change fits two commit types, it is two commits. Changes to GUIDELINES.md or COMMIT.md go in their own `docs(repo)` commit with the reason in the body.

**The test:** every changed line traces directly to the request.

## 4. Goal-driven execution

**Define what "done" means. Work until it is verified.**

Turn each task into a goal you can check:

| Instead of... | Make it... |
| --- | --- |
| "Add a buy-2-get-1 discount" | "Write tests for 1, 2, 3 and 6 items, then make them pass" |
| "Fix the stock count bug" | "Write a test that reproduces the wrong count, then make it pass" |
| "Refactor checkout" | "Checkout tests pass before and after, and no method exceeds V(G) = 10" |
| "Add the low-stock alert" | "A sale that drops stock below the threshold produces exactly one alert; a test proves it" |
| "Write the use case diagram" | "Every role and module in the README appears; it is in `docs/uml/`" |

For a task with several steps, write a short plan first:

```
1. Add StockBatch entity and Liquibase changeset → verify: app starts, migration applies
2. Deduct stock first-expiry-first-out on sale     → verify: unit tests for 1, 2 and 0 batches
3. Publish low-stock event                         → verify: integration test sees one alert
```

Clear goals let you work without constant check-ins. A vague goal ("make it work") needs a question, not a guess.

For the critical methods listed in GUIDELINES.md section 9 (discount calculation, checkout, stock deduction, purchase order receiving), "verified" includes the basis path tests that section describes.

## 5. Before you push

- [ ] The change does what was asked and nothing else (sections 2 and 3).
- [ ] Assumptions are stated in the reply or the commit body (section 1).
- [ ] The success check from section 4 was run, and it passed. Once the build exists, the Maven tests pass.
- [ ] The change passes the review checklist in GUIDELINES.md section 12.
- [ ] The commit message follows COMMIT.md and does not mention Claude or any AI tool.
- [ ] You pulled `main` before pushing, and you are pushing to `main`.

## 6. Reporting back

- Lead with the result: what changed, and where.
- Say exactly what you verified and how. If you could not run something (for example, there is no build yet), say so plainly instead of implying it works.
- List the assumptions you made and anything you noticed but did not change.
- Never disable, skip or delete a failing test to get green. Report it instead.

## How to tell this file is working

- Diffs contain only the requested change.
- Fewer rewrites because something was overbuilt.
- Questions come before the work, not after a mistake.
- Commits are small, focused and pass the commit check the first time.
